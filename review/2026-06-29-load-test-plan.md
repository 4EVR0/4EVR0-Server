# 2026-06-29 정리 — 부하 테스트 현황 / 목표 / 데이터

부하 테스트를 본격적으로 하기 전에, **(1) 지금 있는 건 뭐고 (2) 새로 하려는 건 뭐며
(3) 평가에 쓰는 `dataset.jsonl`은 어떤 데이터인지**를 한 장으로 정리한다.

## 1. 지금 있는 "부하 테스트" — `generate_traffic.sh`

### 형식: **순차(sequential) 트래픽 생성기** (부하 테스트 ❌, 계측 워밍업 ⭕)

- 실제 HTTP API(`POST /api/v1/sessions` → `POST /api/v1/recommend`)를 친다.
- 메시지 6종(스크립트 내장 `MESSAGES` 배열)을 **한 개씩 순서대로** 호출한다.
- 매 요청 사이 `sleep 0.3` → **동시성(concurrency) 없음.** 항상 "한 번에 한 요청".
- 끝나면 `/metrics`를 긁어 단계별 평균 latency·폴백률을 출력하고, `trace_id`로 Loki 조회를 안내.

```
[요청1] --0.3s-- [요청2] --0.3s-- [요청3] ...   (한 줄로 직렬)
```

### 용도 (제작 의도)
- Phase 2(메트릭)·Phase 3(로깅) 인프라가 **실제로 도는지 깨우는** 스모크/데모 도구.
- `recommend_stage_latency_seconds`, `profile_extraction_method_total` 등이 증가하고
  `trace_id`가 Loki로 흘러가는 걸 눈으로 확인하는 용도.

### 한계 (= 지금 하려는 일의 출발점)
- **동시 부하를 못 준다.** GPU(vLLM)에 요청이 몰릴 때 시스템이 어떻게 무너지는지 측정 불가.
- 포화점·tail latency(p95/p99)·타임아웃 캐스케이드 같은 **성능 한계를 드러내지 못함.**

## 2. 지금 하려는 것 — **동시 부하 테스트 + 성능 개선 + before/after 비교**

### 배경: 이 시스템의 병목은 GPU(vLLM, Qwen3-8B-FP8)
추천 1건 = `extract(LLM)` + `neo4j` + `llm_response(LLM)` → **3단계 중 2개가 GPU를 친다.**
현재 LLM 호출(`recommend_service.py`)은 **동시성 제어가 전혀 없어서**, 요청이 몰리면
vLLM에 그대로 다 꽂힌다 → 큐 폭주 → 다수가 `gpu_timeout_seconds(60s)` 타임아웃 → 에러 폭증.

```
동시 50건 → vLLM에 50개 동시 → 큐 폭주 → 타임아웃 캐스케이드(에러율↑, p95↑)
```

### 목표
"파파파팍 동시에 쏟아부었을 때 **어떻게 부하를 관리하고 성능을 개선하는지**"를
**측정 → 개선 → 재측정**으로 증명한다. (오프라인 평가의 MLflow 루프를 인프라 측에 복제)

### 4단계 계획
| 단계 | 내용 | 산출물 |
|------|------|--------|
| 1. 부하 하네스 | 동시 사용자 5→10→25→50 램프업, `/sessions`→`/recommend` 시나리오 | `load/locustfile.py` |
| 2. baseline | 현재 코드로 부하 → **포화점**·병목 단계·에러율 기록 | 측정 결과 |
| 3. 개선 | LLM 호출 앞에 **동시성 제한(`asyncio.Semaphore`)** + (옵션)429 백프레셔 | `config` + `recommend_service` 변경 |
| 4. 재측정 | 같은 부하 재실행 → **p95·처리량·에러율 before/after 표** | `review/...-load-test.md` |

### 측정 지표
- **클라이언트 측**(Locust): p50/p95/p99 latency, 처리량(RPS), 에러율
- **서버 측**(`/metrics`, Grafana): 단계별 latency(어디가 먼저 터지나), 폴백률(rule_based↑ = LLM 장애 신호)

### 기대 효과
세마포어로 동시 호출을 GPU 스위트스팟(예: 4~8)으로 묶으면:
- **에러율(타임아웃 캐스케이드) 급감**, **tail latency(p95/p99) 안정**
- 동작이 "느리게 다 실패" → "안정적으로 처리 + 초과분은 빠른 429"로 건강해짐

### 테스트 데이터는 새로 안 만든다
크롤링/CDC 없이 **기존 `eval/dataset.jsonl`의 메시지를 랜덤 샘플링**해서 부하를 준다.
(아래 3번 참고 — 이미 현실적인 한국어 피부 고민 입력 코퍼스다.)

> 참고: CDC를 안 하는 이유 — 올리브영 크롤링 데이터는 변경분이 거의 없어
> CDC(변경 데이터 캡처)의 실익이 작다. 대신 **부하/성능**이 이 시스템에 더 의미 있는 주제.

## 3. `eval/dataset.jsonl` — 어떤 데이터인가

### 정체: **오프라인 평가용 정답셋(ground truth) 19개**
LLM이 사용자 메시지에서 프로필을 **제대로 뽑았는지 채점**하기 위한 "정답이 달린" 입력 모음.

### 한 줄 스키마
```json
{"id": 1, "label": "건성+주름",
 "message": "피부가 너무 건조하고 당겨요. 요즘 눈가 주름도 신경 쓰이고 탄력이 없어진 것 같아요.",
 "skin_types": ["DRY"],
 "concerns": ["DRY_SKIN", "WRINKLES", "LOSS_OF_ELASTICITY"],
 "constraints": []}
```

| 필드 | 의미 |
|------|------|
| `id` | 케이스 번호 (1~19) |
| `label` | 사람이 알아보기 쉬운 짧은 태그 (예: "지성+여드름") |
| `message` | **실제 사용자가 보낼 법한 한국어 피부 고민 문장** (입력) |
| `skin_types` / `concerns` / `constraints` | **기대 정답** — 이 메시지에서 추출돼야 할 enum 값 |

- 값은 모두 `app/domain/enums.py`의 enum만 사용 (오타·없는 값 0).
- 라벨링 기준은 `eval/LABELING.md`에 팀 합의로 표준화 (예: 증상→피부타입 추론 금지).

### 구성 (커버리지)
- **단일 고민 / 다중 고민 / 제약(향료·비건·저자극·알코올프리·EWG) / 엣지 케이스**를 골고루 포함.
- id18 = "고민 없음"(네거티브, 빈 배열), id19 = "다중 고민"(스트레스 테스트).
- concern 26종 중 25종을 커버.

### 용도 (지금까지)
1. **추출 품질 평가** (`eval/run_eval.py`) — message로 추출 → 정답과 비교 → concern F1·완전일치율 등.
2. **응답 품질 평가** (`eval/run_response_eval.py`) — message로 실제 추천 파이프라인을 돌려 LLM-judge 채점.

### 용도 (앞으로 추가)
3. **부하 테스트 입력 코퍼스** — 19개 message를 랜덤 샘플링해 동시 요청 부하 생성(2번 계획).
   → 정답 라벨(`skin_types` 등)은 부하 테스트에선 안 쓰고, **현실적인 message만** 활용.
