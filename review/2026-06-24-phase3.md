# 2026-06-24 작업 리뷰 (Phase 3 — 앱 측)

## 오늘 한 일: MLOps Phase 3 (앱 측) — 구조화 로깅 + 요청 단위 trace_id

흩어진 stdout 평문 로그를 **JSON 구조화 + 요청 단위 `trace_id`** 로 전환했다.
추천 한 건에서 나온 모든 로그가 같은 `trace_id` 로 묶여, 메트릭 이상 → 해당 요청
로그로 점프하는 추적이 가능해진다. (Loki 수집 인프라는 다음 단계에서 — 아래 "정지 지점" 참고)

---

## 1. 변경 (`4EVR0-Server`)

| 파일 | 내용 |
|------|------|
| `app/core/request_context.py` (신설) | `ContextVar` 기반 trace_id 저장/조회 (`get/set/reset/new`) |
| `app/core/middleware.py` (신설) | 순수 ASGI `TraceIDMiddleware` — 요청마다 trace_id 발급/승계, 응답 헤더, 요청 완료 로그 |
| `app/core/logging.py` (재작성) | JSON 포매터 + trace_id 필터, `plain` 폴백, uvicorn 로거 통합 |
| `app/core/exception_handler.py` | 호출마다 새로 만들던 `request_id` → 현재 `trace_id` 로 통일 |
| `app/core/config.py` | `log_format`(json/plain), `log_level` 설정 추가 |
| `app/main.py` | `TraceIDMiddleware` 등록 |

### 설계 포인트
- **순수 ASGI 미들웨어**로 구현(BaseHTTPMiddleware 아님). ContextVar 를 `__call__` 과
  같은 코루틴에서 set 하므로 다운스트림 엔드포인트까지 trace_id 가 안전히 전파됨
  (BaseHTTPMiddleware 의 알려진 contextvar 전파 이슈 회피).
- **외부 의존성 0** — 표준 `logging` 으로 JSON 출력. t3.small 부담 최소화.
- 기존 `logging.getLogger(__name__)` 코드는 한 줄도 안 고쳐도 자동으로 JSON + trace_id 적용
  (루트 핸들러에 필터/포매터를 거는 방식).
- 들어온 `X-Request-ID`/`X-Trace-ID` 헤더가 있으면 승계 → 게이트웨이/클라이언트와 ID 연속성.

### 로그 한 줄 예시
```json
{"ts":"2026-06-24T...","level":"INFO","logger":"app.request","trace_id":"b95df75e733842dc",
 "message":"request completed","http_method":"GET","path":"/api/v1/recommend","status":200,"duration_ms":0.3}
```

## 2. 검증 (TestClient)

| 검증 | 결과 |
|------|------|
| trace_id 자동 발급 → 엔드포인트 코드/로그/응답 헤더(`X-Trace-ID`) 일관 | ✅ |
| `X-Request-ID` 헤더 승계 → 서버 로그 전부 해당 ID | ✅ |
| 요청 밖 로그는 trace_id 빈값 (격리) | ✅ |
| JSON 1줄 = 1 이벤트, extra 필드(method/path/status/duration) 포함 | ✅ |
| `py_compile` 전체 | ✅ |

> 참고: TestClient(httpx) 자신이 요청 *밖*에서 찍는 클라이언트 로그는 trace_id 빈값이며 정상.

   - → 단순함 기준 (a) 유력하나, 상시 가동 아님 이슈 동일.
