# judge 프롬프트·grounding 원인 규명 (P0-③)

- 날짜: 2026-09-10
- 브랜치: `fix/eval-session-isolation` (커밋 `6e23a3e`)
- 목적: "grounding 2.263" 의 원인 규명 + judge 신뢰성 방어 논거 확보
- 방식: 정적 코드 분석 + 기존 리포트 재분석. **GPU 미가동, 신규 측정 없음**

## 요약 — 결론이 바뀐 부분

**착수 시 세운 가설("grounding 2.263이 현재 문제")은 틀렸다.** 2.263은
2026-06-27 리포트 값이고, 그 원인은 **2026-06-30에 이미 수정됐다**(커밋 `5722a27`).
최신 50건 기준선(2026-07-07)의 grounding은 **4.52**다.

대신 다른 두 가지를 찾았다.

1. 남은 grounding 실패가 **검색 결과 없음(`n_products=0`) 5건에 전부 몰려 있다** — 모델이 실존 제품을 지어낸다.
2. **평가가 운영과 다른 프롬프트를 측정하고 있었다** (수정함).

## 1. grounding 2.263의 실제 원인 — 이미 해결됨

같은 생성 프롬프트(`76af3f07`)·같은 judge 프롬프트(`4603be1a`)로 11분 간격 실행:

| 리포트 | 시각 | grounding | overall |
|---|---|---|---|
| `v5_prod_t0.json` | 2026-06-30 08:27 | **2.053** | 3.747 |
| `v5_prod_t0_fairjudge.json` | 2026-06-30 08:38 | **4.053** | 4.474 |

차이는 커밋 `5722a27` "give judge same evidence context as generator" 하나뿐이다.
judge에게 근거 컨텍스트(성분 근거 수준·제품 핵심성분)를 주지 않으면 응답의 근거 인용을
검증할 수 없어 hallucination으로 오판했던 것이다. `v5_v3_t0` 쌍에서는 1.632 → 4.842로
더 크게 벌어졌다.

**즉 "judge 기준이 과하게 엄격했다"가 아니라 "judge에게 채점할 근거를 안 줬다"가 원인이었고,
이미 고쳐졌다.** 현재 `judge_response()` 독스트링에 그 의도가 남아 있다.

## 2. 생성기 vs judge 컨텍스트 정합성 재검증

두 컨텍스트를 실제 코드로 조립해 비교했다(`_compose_user_content` vs `judge_response`).

| 항목 | 생성기 | judge | 일치 |
|---|---|---|---|
| 성분 목록 잘림 | `[:10]` | `[:10]` | ✅ |
| 제품 핵심성분 잘림 | `[:3]` | `[:3]` | ✅ |
| 근거 라벨(`_evidence_label`) | 있음 | 있음 | ✅ |
| `matched_count` ("핵심 성분 5개 포함") | 있음 | 없음 | ❌ |
| **사용자 리뷰 데이터** (`⭐4.7·리뷰 1234개 · 순해요 82%`) | 있음 | **없음** | ❌ |
| **리뷰 언급 지침** ("리뷰에서는 …라는 평가가 많아요 식으로 덧붙이세요") | 있음 | 없음 | ❌ |

생성기는 리뷰를 언급하라고 **지시받는데** judge는 리뷰 데이터를 못 본다. 구조상 리뷰
기반 문장이 근거 없는 주장으로 보일 수 있다.

**다만 현재는 잠재 위험이다** — 최신 50건 응답에서 리뷰·평점 언급은 **0건**이었다
(`리뷰|평점|별점|⭐|후기` 검색). 프롬프트가 v7로 바뀌며 리뷰 언급이 억제된 것으로 보이나
확정하지 않았다. 리뷰 언급이 다시 늘면 이 격차가 실제 감점으로 나타날 수 있으므로 기록해 둔다.

## 3. 남은 grounding 실패의 정체 — 검색 공백에서의 제품 날조

최신 50건 기준선(`resp-20260707-120755.json`)을 검색 결과 유무로 나눴다.

| 그룹 | n | grounding 평균 | 점수 분포 |
|---|---|---|---|
| 검색 결과 없음 (`n_products=0`) | 5 | **1.6** | 1, 1, 2, 2, 2 |
| 검색 결과 있음 | 45 | **4.844** | 45건 중 39건이 만점 |

실패가 완벽히 한쪽에 몰려 있다. 해당 5건:

| id | 메시지 | grounding |
|---|---|---|
| 18 | 그냥 무난한 데일리 보습 제품 하나 추천해줘요. | 2 |
| 20 | 중성 피부이고 특별한 고민은 없어요. | 1 |
| 45 | 민감성이라 향료·알코올 없고 비건 인증된 저자극 제품만 | 2 |
| 46 | 피부 고민은 따로 없고 비건이면서 EWG 그린 등급 위주 | 1 |
| 47 | 여드름이나 홍조는 없어요. 그냥 평소에 쓸 로션을 | 2 |

공통점: **고민이 명시되지 않아 검색이 빈손** → 모델이 학습 지식에서 실존 제품을 지어낸다.
실제 응답에 등장한 제품: COSRX Advanced Snail 92 Mucin Power Essence,
The Ordinary 100% Organic Cold-Pressed Rosehip Seed Oil, 클리오 클리닉 모이스처라이저.
전부 제공 데이터에 없다.

### 원인 사슬

`_compose_user_content`(`recommend_service.py:794-795`)는 성분 데이터가 없을 때 이렇게 지시한다.

```python
else:
    sections.append("(현재 성분 데이터베이스에 해당 고민에 맞는 성분 데이터가 없습니다. "
                    "일반적인 추천을 제공해 주세요.)")
```

**"일반적인 추천을 제공해 주세요"가 사실상 날조를 지시한다.** 그리고 이때 쓰인
`recommend_response.txt`(base)에는 지어내지 말라는 가드가 **0건**이다. 후속 경로
(`_FOLLOWUP_SYSTEM`)에는 "NEVER invent products, ingredients, studies, or facts"가 있는데,
메인 생성 경로의 base 프롬프트에는 없었다.

| 프롬프트 | 날조 금지 가드 |
|---|---|
| `recommend_response.txt` (base) | 0건 |
| `recommend_response.v2` ~ `v6` | 각 1건 |
| `recommend_response.v7` | 2건 |

## 4. 평가가 운영과 다른 프롬프트를 측정하고 있었다 → 수정

| | 프롬프트 | 해시 |
|---|---|---|
| 운영 기본 (`settings.gen_prompt_name`) | `recommend_response.v7` | `47f37c55` |
| 평가 기본 (`DEFAULT_GEN_PROMPT`, 수정 전) | `recommend_response` | `76af3f07` |
| 2026-07-07 50건 기준선이 쓴 것 | — | `76af3f07` |

**기준선이 운영에서 쓰지 않는 프롬프트를 측정한 값이었다.** 3장의 날조 5건도 가드가
없는 base 프롬프트에서 나온 결과이므로, v7에서도 같은 문제가 남아 있는지는 **재측정 전까지 알 수 없다.**

### 조치 (커밋 `6e23a3e`)

- `DEFAULT_GEN_PROMPT`를 `settings.gen_prompt_name`에서 파생 — 운영 기본이 바뀌면 평가도 따라간다
- run 정보에 `service_gen_prompt`·`service_gen_prompt_version`·`matches_service_prompt` 기록
- 운영 기본과 다른 프롬프트를 평가하면 요약에 경고 출력
- 과거 버전 비교는 `--gen-prompt` 명시 지정으로 유지

테스트 2건 추가(`test_eval_default_prompt_follows_service_setting`,
`test_run_flags_prompt_mismatch_with_service`). 전체 73개 통과.

## 5. GPU 확보 시 확인할 것

우선순위 순.

1. **v7 재측정** — `n_products=0` 5건에서 v7의 가드가 날조를 막는가. 막으면 3장 문제는 프롬프트로 해결된 것이고, 안 막으면 코드 차원의 처리가 필요하다.
2. **세션 격리 A/B** — `--session-mode shared` vs `isolated` 로 오염이 점수에 준 영향 측정.
3. **judge 반복 채점** — `--judge-repeats 3` 으로 `judge_repeat_stddev` 확보. 회귀 판정 임계의 하한 근거가 된다.
4. **사람 라벨 40건** — `--human-labels` 로 MAE·Pearson·Spearman 산출.

## 6. 검색 공백 처리 — 설계 논의 필요

3장의 5건은 프롬프트만의 문제가 아닐 수 있다. 검색이 빈손일 때 취할 동작을 정해야 한다.

| 선택지 | 장점 | 단점 |
|---|---|---|
| 추천 거절 + 되묻기 | 날조 0 | 고민을 안 밝힌 사용자에게 빈손 |
| 데이터 있는 범용 제품으로 폴백 | 근거 유지 | 폴백 후보군을 별도로 정의해야 함 |
| 날조 금지 가드만 강화 (v7 현행) | 구현 비용 0 | 모델 순응에 의존, 완전 차단 아님 |

**결정 전에 1번(v7 재측정)을 먼저 하는 것이 맞다.** v7이 이미 막고 있으면 추가 작업이 불필요하다.

## 7. 면접 답변으로 쓸 수 있는 형태

> judge 점수를 그대로 믿지 않고 먼저 judge 자체를 의심했습니다. 실제로 초기에는
> judge에게 생성기와 같은 근거 컨텍스트를 주지 않아서, 정상 응답을 hallucination으로
> 오판하고 있었습니다. 같은 프롬프트로 컨텍스트만 맞춰 다시 재보니 근거성이
> 2.05에서 4.05로 올랐습니다. **점수가 낮았던 게 아니라 채점 조건이 틀렸던 겁니다.**
>
> 그 다음에는 남은 실패를 유형별로 갈랐습니다. 근거성 미달이 검색 결과가 빈 5건에
> 전부 몰려 있었고, 그때 모델이 실존 제품을 지어내고 있었습니다. 원인은 검색이
> 비었을 때 프롬프트가 "일반적인 추천을 제공하라"고 지시하는 부분이었습니다.
>
> 그리고 이 과정에서 평가가 운영과 다른 프롬프트를 측정하고 있다는 것도 발견해서,
> 평가 기본값을 운영 설정에서 파생시키고 불일치 시 리포트에 경고가 남도록 고쳤습니다.

핵심은 **"judge를 믿는다"가 아니라 "judge를 이만큼 검증했고 이 범위에서만 쓴다"** 로 답하는 것.

## 8. 정정 기록

착수 시 "grounding 2.263이 현재 문제이며 원인은 judge 기준이 과하게 엄격한 것일 수 있다"고
추정했으나, 근거로 삼은 리포트가 2026-06-27 것이었다. 해당 문제는 2026-06-30에
이미 수정됐고 최신 값은 4.52다. 리포트를 시각 순으로 확인하지 않은 것이 원인이다.
