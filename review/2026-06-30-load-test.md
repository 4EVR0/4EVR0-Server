# 부하 테스트 결과 — baseline (2026-06-30)

추천 API(`POST /api/v1/recommend`)에 동시 요청을 단계적으로 늘려가며(5→10→25→50)
**포화점·병목·실패 양상**을 측정한 baseline 기록. 개선(동시성 제한) 전 기준선이다.

## TL;DR

- **병목은 LLM 생성(GPU) 단계가 명백하다.** 부하 중 `llm_response` 평균이 **9.5s → 30.6s(3.2배)** 로 폭증한 반면, `neo4j`는 0.12s로 평탄, `extract`는 1.5s→3.1s에 그쳤다.
- **포화점은 동시 10→25명 구간.** 사용자를 5배 늘려도 처리량(RPS)은 **0.61 → 0.76** 으로 거의 안 올랐다(천장). 단일 8B GPU 서빙의 한계가 그대로 드러남.
- **50명에서 붕괴.** p95가 120s(클라이언트 타임아웃)에 닿고 `/recommend` 요청 **231건 중 20건(8.7%) 타임아웃 실패**.
- 추출 폴백률 0% — 부하로 규칙기반으로 떨어진 건 아니고, **느려지다가 끝내 타임아웃**되는 방식으로 무너졌다.

## 원인 분석 — 왜 이렇게 무너지는가

측정값(2·3절)이 가리키는 근본 원인을 메커니즘 단위로 분해한다. 한 줄 요약:
**"유한한 단일 GPU 처리량 < 들어오는 요청 속도"이고, 그 사이를 막아줄 동시성 제어가 없어 큐가 무한정 쌓이기 때문."**

### ① 근본 원인: 단일 8B GPU의 처리량은 고정인데, 요청당 GPU 작업이 무겁다
추천 1건의 실제 실행 경로(`recommend_service.py`):

```
extract(LLM #1, 짧은 JSON) → neo4j(그래프 조회) → llm_response(LLM #2, max_tokens=1024 긴 생성)
        └─ GPU ─┘                └─ GPU 무관 ─┘            └──────── GPU ────────┘
```

- **요청 1건이 같은 GPU를 2번** 친다(추출 + 생성). 게다가 셋이 **순차(await)** 라 한 요청의 벽시계 시간 = 추출 + 조회 + 생성의 합.
- 생성(LLM #2)은 `max_tokens=1024`의 **autoregressive 토큰 생성** — 토큰을 하나씩 순차로 뽑으므로 본질적으로 무겁고 길다. 워밍업(동시 1명) 때도 9.5s가 걸린 이유.
- GPU가 1장뿐이라 **단위 시간당 생성 가능한 토큰 총량(처리량)은 고정**이다. 이게 RPS 천장(~0.76)의 정체.

### ② 처리량 천장의 정체: 동시성을 늘려도 RPS가 안 오르는 이유
vLLM은 여러 요청을 묶어 처리(continuous batching)하지만, **GPU 연산량과 KV 캐시 메모리가 유한**하다. 동시 요청이 늘면:

- 배치가 커질수록 **요청당 토큰 생성 속도(TPOT)가 느려진다** → 한 요청을 끝내는 데 더 오래 걸림.
- 즉 "더 많이 받는 만큼" 처리량이 비례해서 늘지 않고, 어느 지점부터는 **늘어난 동시성이 전부 지연(대기)으로 흡수**된다.
- 측정에서 RPS가 0.61(10명)→0.71(25명)→0.76(50명)으로 **사실상 평탄**한 게 이 천장의 직접 증거.

### ③ 붕괴의 방아쇠: 동시성 제어 부재 → 무제한 큐잉
앱에는 GPU 앞단의 **동시성 제한이 없다.** 들어오는 모든 요청을 그대로 vLLM으로 흘려보낸다. 그 결과:

- 천장(λ≈0.76 RPS)을 넘는 요청은 **vLLM 큐에 무한정 쌓인다.** 큐 대기시간이 그대로 응답시간에 더해짐.
- **Little's Law(L = λ·W)** 로 보면, 도착률이 처리율을 넘는 순간 큐 길이 L과 대기시간 W가 시간에 따라 **선형 이상으로 발산**한다. 50명 구간에서 p95가 120s(=클라이언트 타임아웃 상한)에 닿은 건 발산이 타임아웃 벽에 부딪힌 결과.
- 그래서 실패가 **50명에서만, 그리고 한꺼번에**(20건) 터진다 — 점진적 열화가 아니라 임계 초과 후 캐스케이드.

### ④ 왜 "꼬리(p95)가 평균보다 먼저" 무너지는가
- continuous batching에서 늦게 도착한 요청은 앞 요청들이 끝나길 기다리거나 큰 배치에 끼어 더 느려진다 → **응답시간 분산이 커진다.**
- p50은 완만(12→26s)한데 p95는 급격(17→41→120s). **SLA는 평균이 아니라 꼬리에서 깨진다** — 평균만 보면 위험을 놓친다.

### ⑤ 왜 폴백(rule_based)은 0%인데도 실패했는가 — 보호장치의 사각지대
- `extract`에는 폴백이 있다(`extract_with_fallback`). 추출은 출력이 짧아 부하에서도 3.1s로 **GPU 타임아웃(60s)을 안 넘겨** 폴백이 안 탔다(폴백 0%).
- 반면 **`llm_response`(생성)에는 동시성 제한도, 빠른 거절도 없다.** 길게 늘어지다 **클라이언트 120s 타임아웃**에 먼저 걸려 실패. 즉 안전장치가 추출만 보호하고 **생성 경로는 무방비**.

### ⑥ 병목이 GPU임을 못박는 교차검증
- `neo4j` 0.12s로 **완전히 평탄** → DB·네트워크·앱 이벤트루프는 병목이 아니다(앱 핸들러는 async라 await 동안 GPU 응답만 기다림, CPU 블로킹 아님).
- `extract` 1.5→3.1s, `llm_response` 9.5→**30.6s**. 둘 다 GPU 단계만 부하에서 악화 → **악화의 출처는 공유 GPU 경합** 하나로 수렴.

### 메커니즘 단정과 측정의 경계 (정직성)
①②③의 "vLLM 큐가 쌓인다 / TPOT가 느려진다"는 **메커니즘 추론**이다. 본 테스트가 직접 잰 건 *앱 측 단계별 latency*까지다. 이 추론을 **수치로 못박으려면** vLLM `/metrics`의
`vllm:num_requests_waiting`(큐 길이), `vllm:num_requests_running`, `vllm:gpu_cache_usage_perc` 를
부하 중 Grafana로 같이 떠서 "50명 구간에서 waiting이 발산하는지"를 확인하면 된다. → after-semaphore 재측정 때 함께 캡처 권장.

## 2. 단계별 결과 (클라이언트 측, Locust)

| 동시 사용자 | RPS(평균) | p50 | p95 | p99 | 실패 |
|:---:|:---:|:---:|:---:|:---:|:---:|
| 5  | 0.22 | 12s | 17s  | 17s  | 0 |
| 10 | 0.61 | 13s | 18s  | 19s  | 0 |
| 25 | 0.71 | 15s | **41s** | 44s | 0 |
| 50 | 0.76 | 26s | **120s(timeout)** | 120s | **18** |

**해석**
- **RPS 천장 ≈ 0.7~0.8.** 10명 이후로는 사용자를 늘려도 처리량이 안 오른다 → 이미 포화(GPU가 천장).
- **꼬리(tail)가 먼저 무너진다.** p50은 완만히 오르지만 p95는 18s→41s→120s로 급격히 꺾임. SLA(예: 10s)는 동시 5명에서 이미 초과.
- **50명에서 캐스케이드 실패.** 대기열이 120s를 넘겨 타임아웃이 누적(8.7%).

`/recommend` 종합: 요청 231건, 실패 20건(8.7%), p50 38s, p95/p99 120s(타임아웃 상한).

## 4. 결론 — 무엇이 문제인가

1. **단일 8B GPU 서빙 + 동시성 제어 부재**가 실재 병목. 동시 요청이 vLLM 큐에 그대로 쌓여 생성 지연이 선형 이상으로 증가하고, 끝내 클라이언트 타임아웃으로 캐스케이드된다.
2. 현재 동작은 **"느리게 다 같이 죽는"** 패턴 — 부하가 몰리면 모든 요청이 함께 느려지다 일부가 타임아웃. 빠른 거절(429)도, 보호장치도 없다.

## 5. 다음 단계 (개선 적용)

개선은 **두 축**으로 나뉜다. 둘은 택일이 아니라 보완재다.

- **축 A — admission control(세마포어/429):** 처리량 천장은 그대로 두고, 받아준 요청의 지연만 지키고 붕괴를 막는 **안전벨트**. 본질은 *거절*이라 "더 많이 처리"하지는 못한다.
- **축 B — 천장 자체 올리기(GPU 최적화):** 같은 시간에 GPU가 더 많은 요청을 처리하게 만드는 **엔진 출력 키우기**. → 6절.

README의 계획(축 A):

1. LLM 호출 앞에 **`asyncio.Semaphore`** 동시성 제한 추가 (`config`에 `llm_max_concurrency`).
   - 기대: GPU에 동시 N개만 흘려보내 생성 latency 안정 → **p95/p99 안정 + 에러율 급감**.
   - 옵션: 초과분은 빠르게 **429**로 거절해 "느리게 다 실패"를 "안정 처리 + 초과는 즉시 거절"로 전환.
2. `TAG=after-semaphore ./load/run_load_test.sh` 로 재측정 → 본 문서에 before/after 표로 추가.

> ⚠️ 세마포어만으로는 RPS 천장(~0.76)이 안 올라간다. 천장을 올리려면 6절을 함께 적용하고,
> 세마포어는 "그래도 넘칠 때"의 보호장치로 둔다.

## 6. GPU 최적화 옵션 — 천장(처리량) 자체 올리기

세마포어가 "받은 것만 보호"하는 안전벨트라면, 아래는 **RPS 천장 자체를 끌어올리는** 작업이다.
현재 셋업(단일 GPU, `Qwen/Qwen3.5-9B`, vLLM, 요청당 LLM 2회, `gen_max_tokens=1024`) 기준 ROI 순으로 정리.

### A. 요청당 GPU 일을 줄이기 — 코드/설정, 비용 0, 효과 큼

| # | 레버 | 원리 / 기대효과 | 근거·확인 포인트 |
|---|------|----------------|------------------|
| ① | **`max_tokens` 적정화** | 생성은 토큰 1개=forward 1회라 **응답시간 ∝ 출력 토큰 수**. 1024가 과하면 줄인 만큼 생성시간 단축 → 천장↑ | issue #24로 1024로 키운 값. vLLM `request_generation_tokens` 히스토그램으로 **실제 출력 길이 분포 실측 후** 적정화 |
| ② | **프리픽스 캐싱** | 모든 요청이 공유하는 정적 시스템 프롬프트(추출 2.6KB + 응답 2.3KB ≈ ~1,300토큰) prefill을 1회만 계산·재사용 → 요청당 연산↓ | **측정상 `vllm:prefix_cache_hits_total = 0`** (queries도 0). 현재 효과 없음 → `--enable-prefix-caching` 활성/검증이 즉효 가능성. (0이 서버 재시작 탓일 수도 → 부하 중 hit율 재확인 먼저) |
| ③ | **시맨틱 캐시(Redis)** | 유사 질의("건조", "각질"…)의 추천 결과를 정규화 프로필 기준 캐시 → **캐시 히트 = GPU 0원** | Redis 이미 사용 중. 유효 처리량을 통째로 올리는 가장 직접적 방법 |
| ④ | **요청당 LLM 2회 구조 재검토** | `extract`+`generate`로 GPU를 2번 침. 추출을 더 작은 모델 / guided-JSON decoding / 규칙기반 우선+LLM 폴백으로 GPU 1회 절감 | `recommend_service.py` extract·llm_response 두 stage |

### B. 같은 GPU를 더 잘 굴리기 — vLLM 서빙 튜닝

| # | 레버 | 원리 / 기대효과 | 확인 포인트 |
|---|------|----------------|-------------|
| ⑤ | **양자화(FP8/AWQ)** | 가중치 메모리↓ → **KV캐시 여유↑ → 동시 처리 요청↑ + 속도↑** | `.env` 기본값이 한때 `Qwen3-8B-FP8`였으나 실서빙은 `Qwen3.5-9B`. **현재 FP8/FP16 여부 확인** 후 FP16이면 FP8/AWQ 전환 |
| ⑥ | **KV캐시·배치 파라미터** | `--gpu-memory-utilization`(예 0.9), `--max-num-seqs`, `--max-num-batched-tokens` 상향 → 절벽 전 더 많은 요청 동시 배칭 | `vllm:num_requests_waiting_by_reason{reason="capacity"}` 게이지로 capacity 한계 모니터 |
| ⑦ | **Chunked prefill** | `--enable-chunked-prefill`로 prefill·decode를 잘게 교차 → 긴 프롬프트가 타 요청 decode를 막지 않음 → **부하 시 p95 안정** | 꼬리 latency 개선용 |
| ⑧ | **Speculative decoding** | draft 모델/n-gram으로 생성 1.5~2배 가속 | 효과 크나 구성 복잡도↑ → 후순위 |

### C. 천장을 돈으로 올리기 — 수평/수직 확장

| # | 레버 | 원리 |
|---|------|------|
| ⑨ | **레플리카 + 로드밸런서** | GPU 인스턴스 N개 분산 → 처리량 **거의 선형** 확장. "더 많이 처리"의 정공법 |
| ⑩ | **더 큰 GPU / 텐서 병렬** | 메모리·연산 큰 카드 또는 멀티 GPU 분할 |

### 권장 적용 순서 (현재 셋업)
1. **프리픽스 캐싱 hit율 확인/활성화** (무료, 즉효 가능) — 측정상 현재 0
2. **`max_tokens` 실측 후 적정화** (무료, latency 직접 단축)
3. **시맨틱 캐시(Redis)** (유효 처리량 통째로↑)
4. **FP8 양자화 확인/적용** + KV캐시 파라미터 튜닝
5. 그래도 부족하면 **레플리카 수평 확장**
6. 위로 천장을 올린 뒤 **세마포어/429는 "그래도 넘칠 때"의 안전망**으로 병행

> 한 줄: **세마포어는 안전벨트, 1~5는 엔진 출력 자체를 키우는 작업.** 천장을 올린 다음 안전벨트를 채운다.

## 8. Track 1 심화 — reject 모드(429) & concurrency 스윕 (2026-07-01)

세마포어를 **어떻게 설정하면 최적인가**를 두 실험으로 특성화. 둘 다 admission control의 변형이라
RPS 천장은 못 올린다(Track 1) — 바뀌는 건 *초과분 처리 방식*과 *동시성 N*뿐.

### 8.1 reject 모드 — 초과분 즉시 429 (N=8)
설정: `llm_max_concurrency=8`, `llm_reject_over_capacity=True`. 빈 슬롯이 없으면 대기 없이
`LLMOverCapacityError → HTTP 429`. baseline과 동일 staged 프로파일.

| 구분 | 값 |
|------|---:|
| 성공(200) | 213건 |
| **거절(429)** | **3,985건 (95%)** |
| timeout/5xx 실패 | 0 |
| 성공 요청 서버측 생성(`llm_response`) 평균 | **7.3s** |
| 거절 응답시간 | ~0.04s (즉시) |

**queue 모드(7절)와 직접 비교 — 같은 N=8, 같은 부하:**

| | queue (N=8) | reject (N=8) |
|------|---:|---:|
| 성공 처리수 | 229 | 213 (≈동일) |
| 성공 요청 생성 latency | 26.1s | **7.3s** |
| timeout 실패 | 0 | 0 |
| 초과분 처리 | 큐에서 대기(백로그 누적) | **즉시 429 거절(3,985건)** |
| 클라이언트 경험 | "다 받아주지만 느림"(p95 84s) | "받아준 건 빠름, 대부분 '지금 바쁨'" |

**해석**
- 두 모드의 **성공 처리량은 같다**(~0.5 RPS, GPU 천장). 차이는 오직 **초과분을 어떻게 하느냐**.
- reject는 큐 대기가 없어 **받아준 요청의 latency를 낮게 유지**(생성 26.1→7.3s). 대신 과부하 시 **대다수를 즉시 거절**.
- 거절수 3,985가 큰 건 locust가 429 직후 곧바로 재시도하기 때문. 실제 클라이언트가 백오프하면 줄지만, "용량 초과 시 빠르게 신호를 준다"는 성질은 동일.
- **선택 기준:** 사용자가 *느린 응답*보다 *"지금 혼잡, 잠시 후"* 를 선호하면 reject. *모든 요청을 결국 처리*해야 하면 queue.
- ⚠️ **측정 주의:** locust는 429를 '실패'로 집계 → reject 모드의 클라이언트 p50(42ms)은 거의 429라 '성공 요청 latency'가 아니다. 성공 요청 지표는 **서버측 stage(생성 7.3s)** 로 봐야 정확.

### 8.2 concurrency 스윕 — N=4/8/12/16 (queue, 고정 50u·2분 sustained)
방법: 50명을 처음부터 2분간 그대로 가하는 **sustained-overload**(staged 램프와 다름 →
**절대값을 7절 표와 비교 금지**, N 간 상대 비교용).

| N | 완료 | 실패 | p50(s) | p95(s) | RPS | 서버 생성평균(s) | 거절 |
|:---:|---:|---:|---:|---:|---:|---:|---:|
| 4  | 37 | 0 | 68 | 108 | 0.32 | **56.0** | 0 |
| 8  | 46 | 0 | 71 | 108 | 0.39 | 58.6 | 0 |
| 12 | 36 | 0 | 76 | 109 | 0.32 | 66.1 | 0 |
| 16 | 40 | 0 | 78 | 109 | 0.36 | 64.8 | 0 |

**해석**
- **N을 올려도 처리량이 안 는다**(RPS 0.32~0.39 평탄). 단일 GPU가 천장이라 동시성을 더 줘도 천장은 그대로.
- 오히려 **N↑일수록 per-request 생성이 느려진다**(56→66s). 동시 호출이 많을수록 vLLM 배치가 커져 KV캐시·연산 경합으로 TPOT가 악화(thrash).
- 전 구간 **실패 0**(queue가 보호). p95가 108s로 비슷한 건 50명 sustained가 N과 무관하게 깊은 큐를 만들기 때문.
- **결론: GPU의 유효 동시성은 작다 → 세마포어 N은 작게(≈4~8)가 최적.** 큰 N은 thrash만 더한다. N=8이 RPS 미세 우위(노이즈 범위 내).

### 8.3 Track 1 종합 권장
- **기본값: `llm_max_concurrency=8`, queue 모드** — 실패 0, 모든 요청 결국 처리.
- **빠른 응답이 중요한 프런트 경로: reject 모드(429)** — 받아준 요청은 빠르게, 초과분은 즉시 거절 + 클라이언트 백오프.
- **N은 키우지 말 것** — 천장은 안 오르고 thrash만 는다. 천장은 **Track 2(6절)** 로만 올라간다.
- 다음: Track 2 진입(프리픽스 캐싱부터) → 천장 올린 뒤 N·reject 임계 재튜닝.
